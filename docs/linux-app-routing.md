# Linux application routing without TUN

KokoroBox routes selected Linux applications through Mihomo without TUN. Desktop owns rules and Mihomo configuration; the root `kokorobox-service` owns process classification, policy routing, and netfilter state.

## Traffic path

```text
selected process
  -> protocol/action cgroup
  -> iptables cgroup match
  -> fwmark 0x4b42
  -> policy-routing table 20269
  -> loopback PREROUTING TPROXY
  -> Mihomo listener 0.0.0.0:7894
```

The listener is a Mihomo `tproxy` listener, not a SOCKS listener. The service installs an INPUT guard that rejects direct non-loopback access to port 7894. Traffic generated by KokoroBox, Mihomo and the service cannot be selected as an application-routing target.

When **Proxy application UDP DNS** is enabled, UDP and TCP port 53 traffic from Proxy cgroups is redirected to Mihomo's DNS listener at `127.0.0.1:7892`. No system-wide DNS setting is changed.

## cgroup backend selection

The service chooses one backend at startup:

1. `linux-cgroup-v2`: selected when `/sys/fs/cgroup/cgroup.controllers` exists and the installed `xt_cgroup` matcher supports `--path`.
2. `linux-cgroup-v1-net-cls`: used only when v2 is unavailable or unusable. The service reuses an existing `net_cls` hierarchy, or mounts a private hierarchy below `/run/kokorobox/cgroup/net_cls`.

The active backend is returned by the process-router status API and shown next to the TPROXY endpoint in the UI.

## Requirements

- Linux x86_64 or arm64.
- A root-owned, running KokoroBox Service. Application routing always uses the service even when Mihomo itself uses the Desktop's direct/elevated launch mode.
- `ip`, `iptables`, and `ip6tables` from trusted root-owned paths.
- Kernel support for TPROXY, policy routing and the cgroup netfilter matcher.
- For the fallback only: cgroup v1 `net_cls` and `mount`/`umount`.

Official packages declare user-space dependencies; kernel support varies by distribution. Desktop sends authenticated policy and lifecycle requests to the service.

## Rule and lifecycle semantics

- Linux rules can match either an exact, absolute executable path or an exact executable name. Name matching uses the basename reported by `/proc/<pid>/exe`, so it remains stable across symlinks and versioned installation directories. Wildcards are rejected.
- Executable-name matching affects every process with that name; use full-path matching when different applications share a filename.
- Proxy, Direct and Block each have TCP, UDP and combined cgroups.
- The service scans `/proc` and moves matching processes into the corresponding cgroup. Children normally inherit their parent's cgroup.
- Restart the selected application after adding, removing or changing a rule. This closes existing sockets and gives the classifier a clean process lifetime.
- If Mihomo port 7894 is unavailable, Proxy rules are translated to Block before the service acknowledges the policy.
- On disable, lease expiry, service shutdown or failed firewall installation, the service restores tracked processes, removes its exact ip rules/routes and deletes only the `KOKOROBOX_*` chains it owns.

## Current boundary

Independently launched processes are classified by short-interval `/proc` polling, so a new process can open a socket before its first scan. Child processes normally inherit the assigned cgroup. This is not a zero-race launch boundary.

The DNS redirect covers ordinary UDP/TCP port 53 queries issued by a Proxy-rule process after classification. Applications using built-in DoH/DoT are ordinary application traffic and follow the selected Proxy action rather than the DNS redirect.

## Diagnostics

The following checks should be collected from the affected Linux host:

```sh
test -f /sys/fs/cgroup/cgroup.controllers && echo cgroup-v2
iptables -m cgroup --help
ip rule show
ip route show table 20269
iptables-save | grep KOKOROBOX_
ip6tables-save | grep KOKOROBOX_
```

If neither cgroup backend can be prepared, KokoroBox leaves application routing in the error state and does not report the firewall as ready.
